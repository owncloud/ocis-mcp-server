# Design: MCP spec 2026-07-28 and OIDC inbound for the HTTP transport

Status: **gates answered, awaiting design approval.** Gates G1 to G8 in `DECISIONS.md` were resolved by
accepting the recommended option at each. Nothing is built until this document is approved.

## Decisions

| Gate | Decision |
|---|---|
| G1 | Stay on go-sdk v1.8.0. Serve 2026-07-28 and older clients through SDK negotiation. Re-pin when v1.9.0 is stable. |
| G2 | `Stateless: true`. Cache hints: discover and list methods `ttlMs=300000` public, `resources/read` `ttlMs=30000` private. Missing resource gives `mcp.ResourceNotFoundError`. |
| G3 | Modes `oidc`, `secret` (deprecated, startup warning) and `none` (loopback only), one per instance. Unset mode is inferred. Both issuer and secret set is a startup error. |
| G4 | Local JWT validation, no introspection. Library `golang-jwt/jwt/v5` plus our own discovery and JWKS cache. Rules as in `DECISIONS.md` G4.3. Built-in IdP unsupported for inbound OIDC in v1, Keycloak supported. The dependency issue is not yet opened and needs a separate OK before the PR. |
| G5 | Outbound stays one service credential, with an audit log of verified `iss` and `sub`. Token exchange is a later phase, not in this effort. Inbound tokens are never forwarded. |
| G6 | One required scope in v1, enforced by SDK middleware. No per-tool categories and no step-up in v1. |
| G7 | Inbound `OCIS_MCP_HTTP_*`, outbound `OCIS_MCP_OCIS_*`, old names as deprecated aliases, dead `OCIS_MCP_OIDC_*` variables warn. Full table in `DECISIONS.md` G7. |
| G8 | One release, v1.2.0, with a prominent HTTP behavior note. We write the CHANGELOG entry only. |

Smaller calls accepted with the gates: `http.Server` timeouts, SDK Origin protection checked and extended if needed,
a `make reuse` target and CI step, conformance harness tried in Phase 1, Roots, Sampling and Logging untouched.

## Intent

The server cannot be used by a 2026-07-28 client over HTTP today, and its only inbound control is one
shared secret with no caller identity. We move the HTTP transport to the 2026-07-28 spec and add real
OAuth 2.1 resource-server behavior backed by OIDC, so operators can put the server on a network under
their own identity provider.

## Goals

- 2026-07-28 clients work over HTTP and stdio. 2025-11-25 clients keep working.
- HTTP can authenticate callers with OIDC access tokens: metadata discovery, validation, audience binding, spec-shaped challenges.
- Verified caller identity (`iss`, `sub`) is available per request and logged for audit.
- Existing deployments keep working. Old settings stay as deprecated aliases.

## Non-goals

New tools. DCR and CIMD. Roots, Sampling, Logging. Tasks, MCP Apps and Enterprise Managed Authorization.
Changes in owncloud/ocis. New OCS dependencies. Multi-tenancy. Outbound identity beyond G5(a) in this effort.

## Anti-goals

- Forwarding the inbound token to oCIS, in any form.
- Accepting a token because its `azp` matches, the way oCIS does.
- A mode where the shared secret and OIDC are both accepted.
- Logging a token, a JWT or a claim body.
- Calling anything other than the configured issuer and oCIS.

## Constraints

- go-sdk v1.8.0. Prefer its `auth` primitives, write our own code only where it has none (A§3).
- No new dependency without an issue (`AGENTS.md`). Only G4.2 may add one.
- stdio keeps environment credentials. No OIDC flow there.
- Issuer URL and public base URL are operator-configured. No hardcoded public URLs, no telemetry.
- Table-driven tests, no skipped tests, no TODO comments. Signed and DCO-signed conventional commits.

## Approaches considered

| Approach | Trade-off |
|---|---|
| 1. SDK-native middleware plus our own `TokenVerifier` (recommended) | The SDK covers metadata serving, bearer parsing, 401 and 403 mechanics and expiry. We write discovery, JWKS cache and claim checks. Smallest code we own that is security-sensitive. |
| 2. Authenticating reverse proxy in front (oauth2-proxy, Envoy) | No auth code in this repo. But the spec requires the MCP server itself to serve protected resource metadata and bind the audience. The proxy must still pass identity to us. Shifts the problem and fails the "single binary" use. |
| 3. Our own complete OAuth stack | Maximum control, maximum risk and review cost. Nothing here needs it. |

Chosen for the draft: approach 1.

## Design (draft)

### Phase 1: transport

- `mcp.NewStreamableHTTPHandler` with `StreamableHTTPOptions{Stateless: true, PropagateRequestCancellation: true}`. The SDK then serves
  2026-07-28 and legacy requests. Cancellation propagation is needed because closing the stream cancels a 2026-07-28 request and the SDK default does not stop the handler.
- `ServerOptions.SetCacheable` with the G2 values. Resource handlers return `mcp.ResourceNotFoundError`.
- Test matrix: in-process SDK client over stdio and HTTP at 2026-07-28, and a client pinned to 2025-11-25 over HTTP.
  Assert `resultType`, `Mcp-Method` and `Mcp-Name` handling, `-32602` for a missing resource, cache hints on lists, GET returns 405.
- Conformance harness against our server if it can target it.
- Tooling gates: `make test`, `make lint`, a new `make reuse` and `make docker-build` green.
- Adjacent hardening: `http.Server` timeouts, SDK Origin protection checked and extended if needed.

### Phase 2: inbound OIDC

Request path in mode `oidc`:

```
client -> SecurityHeaders -> [public route: GET /.well-known/oauth-protected-resource/mcp]
                          -> RequireBearerToken(verifier, {ResourceMetadataURL, Scopes}) -> Streamable handler -> tool
```

- **Protected resource metadata.** Served by `auth.ProtectedResourceMetadataHandler` at the path-suffixed well-known URI for
  the `/mcp` resource, public and unauthenticated. `resource` is the canonical URI. `authorization_servers` is the configured issuer.
  `scopes_supported` is the configured scope. The same URL is the `resource_metadata` value in every challenge.
- **Verifier** (`internal/auth`, new). Implements `auth.TokenVerifier`:
  1. Reject empty tokens and anything not from the `Authorization` header.
  2. Parse with the G4.3 rules: allow-listed algorithms, `iss`, `aud` via `MatchesResource`, mandatory `exp` and `sub`, `nbf` when present, 60 s leeway.
  3. Resolve the key by `kid` from the JWKS cache.
  4. Return `TokenInfo{UserID: sub, Scopes, Expiration, Extra: {iss}}`. Wrap failures in `auth.ErrInvalidToken`.
- **Discovery and JWKS** (`internal/auth`). OIDC Discovery, then RFC 8414. Issuer in the document must match config. Cache and refresh per G4.3, with a
  rate-limited refetch on unknown `kid` and singleflight.
- **Identity to handlers.** Tool handlers read `req.Extra.TokenInfo`. A small helper logs `iss`, `sub`, tool name and outcome per call.
  The outbound client is unchanged (G5(a)): `applyAuth` still uses the service credential.
- **Config.** Per G7. Validation: mode `oidc` requires issuer and public URL. The issuer and `jwks_uri` must be https, except that plain http
  is allowed for a loopback host. Issuer and secret both set without an explicit mode is a startup error. With an explicit mode, that mode wins
  and the unused credential setting logs a warning. Exactly one verifier is ever active, so a secret never works in `oidc` mode.
  `OCIS_MCP_HTTP_PUBLIC_URL` must be an origin with no path. The endpoint path is fixed at `/mcp`.
- **stdio.** Untouched.

### Phase 3: docs and release

README auth and "Securing the HTTP transport" sections, env var table, GETTING_STARTED, CHANGELOG (G8), `AGENTS.md`, Dockerfile check,
`.goreleaser.yml` check, `evaluation.xml` validity, an example OIDC client config for HTTP. State the shared-identity limitation
plainly, since G5(a) does not remove it.

## Calls made after the builder check

The builder check raised seven questions. All were settled as my calls and none changed the gates.

1. Keycloak integration test: a realm import file in the repo, a build tag `integration` and a `make test-integration` target. It is not part
   of the default CI run in this effort, so the unit tests carry the coverage gate. The README documents how to run it.
2. Audience: the accepted `aud` and the `resource` advertised in the metadata are the same canonical URI. There is no audience override setting,
   because an override would let metadata and tokens disagree or let an operator accept a client ID. The setting `OCIS_MCP_HTTP_OIDC_AUDIENCE` is dropped.
3. Path: `OCIS_MCP_HTTP_PUBLIC_URL` is an origin with no path, validated at startup. A reverse proxy that mounts the server under a prefix is not
   supported in v1.
4. Secret and issuer both set: as in the Config bullet above. This also corrects the earlier wording that read as if both were always an error.
5. Insecure issuer: no new setting. https is required, with a loopback exception. Existing outbound skip-verify flags are not reused.
6. Delivery: one branch, one PR at the end, with commits per phase. Phase 1 fixes a real breakage on its own, so I can split it into a separate
   PR if you prefer. The dependency issue gates the Phase 2 merge, not the branch.
7. If `req.Extra.TokenInfo` is empty in stateless mode, identity travels from `auth.TokenInfoFromContext` through the request context into the handlers.
   This does not reopen G1 or G2. The first Phase 2 test checks it.

## Testing outline

Phase 2 table-driven cases: valid token, expired, wrong `aud`, wrong `iss`, bad signature, `alg: none`, HS256 signed with the public key as secret,
missing header, token in query string, missing required scope, missing `exp`, missing `sub`, JWKS rotation with a new `kid`, unknown `kid` rate limit,
stale-if-error and discovery issuer mismatch. Integration test against Keycloak from the `ocis_full` compose example. Tokens never appear in test output.
